# Backlog 0003: Coffer web client — prototype core loop on mock data

**Status:** Open  ·  **Priority:** High  ·  **Surfaces:** app  ·  **Opened:** 2026-08-22
**Epic:** Foundation — first usable expense tracker

## Context / problem

Every screen in this product is still hypothetical. The Epic's phase 2 note says the API response shape "is a contract — pin it in the ticket before phase 3 starts", and today there is nothing to pin it against: we would be designing a JSON shape with no idea what the ledger view or the entry form actually needs from it.

A clickable prototype on mock data inverts that. The client is built first against a mock network layer, and the mock handlers become the **draft** of the phase-2 API contract — written by the consumer that has to live with it, rather than guessed at by the producer.

The prototype also carries auth screens. That does **not** mean the product has auth: the Owner confirmed on 2026-08-22 that this stays localhost-only, so the CANDIDATES question "Does this ever leave localhost?" remains open and no ADR is made here. Login is prototyped as a UI surface so the shell has a real unauthenticated/authenticated split; the day hosting is wanted, auth + TLS + an `ops` gate get ticketed together and this prototype is what they render.

**Auto-persisted:** No — Owner approved 2026-08-22. Fails the rubric on three signals: change type (addition), product decision (auth shape, product name), contract (the mock handlers draft the API response shape).

## Goal & non-goals

- **Goal:** a runnable web client where the Owner can log in, see a ledger, enter a transaction, watch it appear with a correct amount, correct a mistake, and triage what is uncategorized — all against mocked network responses, no backend running. **This is the core loop: the smallest thing that is genuinely usable and can be judged.**
- **Scope was chosen by the Owner on 2026-08-22** from a candidate function list of sixteen; thirteen were selected. This ticket carries five of them and [0004](0004-app-prototype-accounts-transfers-insight.md) carries the other eight. The three declined are named as non-goals below so they are not quietly reintroduced.
- **Goal:** MSW request handlers that are readable as a proposed API contract, so phase 2 of the Epic can be ticketed from evidence instead of speculation.
- **Non-goal: real authentication.** No password hashing, no server-side session store, no credential leaving the browser, and no password reset. The screens are real; what sits behind them is not. ~~*and no second account — first-run setup provisions exactly one*~~ — **struck 2026-08-25** by the third Owner directive below and [ADR 0004](../decisions/0004-multi-user-tenant-scoped-from-day-one.md): sign up is open and any number of accounts may exist. Left visible rather than deleted, because an agent reading top-down hits this line before the directive.
- **Non-goal:** any work in `../projects/api`. This ticket does not touch the backend surface.
- **Non-goal:** locking the API contract. The handlers are a *draft*; promoting them to the pinned contract is a separate Owner-gated step.
- **Non-goal:** import, budgets, recurring transactions, and nested categories — all four are unresolved in CANDIDATES. Categories here are **flat**.
- **Non-goal — declined by the Owner, 2026-08-22:** spending-over-time trend (needs months of real data to say anything), CSV/JSON export (would export fixtures and prove little now), and a settings screen (currency and date format are fixed by ADR 0003, leaving little to put in it). Each is a reasonable later ticket, not a gap in this one.
- **Non-goal — deferred to [0004](0004-app-prototype-accounts-transfers-insight.md), not dropped:** accounts management, transfers between accounts, category CRUD, the month summary, spending by category, and the dashboard. **There is no dashboard yet** — until 0004 lands, a successful login lands on **the ledger**; 0004 introduces the dashboard and moves the landing route there.
- **Non-goal:** visual polish as a deliverable. This is a prototype for shaping the contract and the entry flow, not a design sign-off.
- **Non-goal: automated tests.** Owner decision, 2026-08-22. Closing evidence is a green build plus observed dev-server behavior, not test counts.

## Plan (by phase)

Five Owner-selected functions, grouped so each phase is independently demonstrable.

**Owner directive — 2026-08-25 (third): conventional login + sign up.** *"tôi muốn có màn hình login & sign up dạng truyền thống, để có thể sau này đẩy lên cloud cho mọi người dùng"*

This replaces phase 2's first-run-provisioning model. **Both screens are permanently reachable**, cross-linked the way any signed-up product does it — sign up is no longer a screen that disappears once one account exists.

**It also puts a written product constraint under revision, which is why it is recorded here and not just built.** `CLAUDE.md` opens with *"Single user, no multi-tenancy. There is no organization, no sharing, no roles. Don't build for tenants that don't exist."* "Đẩy lên cloud cho mọi người dùng" is exactly that tenant. The constraint is not overridden by this entry — only the Owner can do that, and it is a `CLAUDE.md` edit plus an ADR, not a ticket note.

**Split, because the two halves cost different amounts:**
- **The screens are cheap and are being built now** (phase 2b below). A prototype's sign-up screen is a form; it commits nothing.
- **Multi-tenancy is not cheap and is not being built.** It reaches every table, every query, and every endpoint. **The question is in front of the Owner now rather than later because [0001](0001-api-ledger-foundation.md) has not written a line of schema yet** — a `user_id` added to an empty schema is free; retrofitted onto real rows it is a migration with a data-loss edge. See [CANDIDATES](../decisions/CANDIDATES.md).

**Note for the surface agent:** the conflict between this directive and `CLAUDE.md`'s single-user line is **known and already escalated**. Build the screens; do not halt on it.

**Owner directive — 2026-08-25 (second, and it reverses this ticket's premise).** After phase 2 landed, the Owner read the shape of what had been built and stopped it: *"khi nói về mock data, dường như bạn đã làm quá lên, thực sự mong muốn của tôi chỉ là build ui và bấm qua lại đc, để xây dựng ui ux, chúng ta đâu cần mock server?"*

The measurement that settled it: **1.343 lines of mock-server machinery against 858 lines of actual UI**, of which ~400 lines were a fake auth server (`POST /api/session`, bearer tokens, 401/409) standing behind a login screen whose real job is to let the Owner click through to the next screen.

**What is now true:**

- **The mock network layer is deleted, not paused.** MSW, the service worker, `handlers.ts`, `store.ts`, `owner-store.ts`, `api/client.ts`, `dev-server/` — all out. Screens import JSON directly and hold their state in React. Login flips a boolean; it does not call an endpoint.
- **This ticket no longer drafts the API contract.** That was its stated reason for existing ("the mock handlers become the *draft* of the phase-2 API contract, written by the consumer"). The Owner has chosen click-through UI/UX over contract drafting. **The Epic's phase 2 must now define its own request/response shapes** — nothing downstream produces a draft for it any more. This is recorded in `STATUS.md`'s Epic table so `api` cannot inherit a draft that stopped existing.
- **What survives the deletion:** the JSON fixtures, the money module, the calendar-date module, the type definitions (they are where the money contract lives in the client), and every screen built so far — ledger, filters, setup, login, shell.
- **Transaction entry keeps a visible loop.** State is lifted to one shared place rather than scattered per-route, so a transaction entered in phase 4 appears in the ledger during the session. Entry speed is the product's stated feature and cannot be judged if a new row vanishes on submit. A reload re-seeds from JSON — accepted by the Owner.
- **PM note, for the record:** the over-build was the PM's brief, not the agent's improvisation. The agent built what it was told and flagged its own additions. The 2026-08-22 framing invited contract-drafting, but nothing forced the PM to commission a fake auth server for a login screen — the conflict should have gone to the Owner before delegation, not after.

## Contract

The prototype honors the money contract from CLAUDE.md and the field names pinned in 0001, so the mock and the eventual API do not diverge:

- Amounts are signed integers in minor units, JSON field `amount_minor` as a **number**. No floats, no decimal strings, no client-side arithmetic that leaves integer space.
- **Currency is VND, exponent 0** ([ADR 0003](../decisions/0003-currency-vnd-single-exponent-zero.md)). Fixtures are stated in đồng — a 30.000 ₫ coffee is `amount_minor: 30000`, **not** `3000000`. Every rendered amount goes through the 0002 module; no component formats or divides on its own.
- Sign is direction: outflow negative, inflow positive. Neither category nor account may imply it.
- `occurred_on` is a calendar date `YYYY-MM-DD`, never a timestamp.
- No per-row currency field, no currency column, no conversion.
- No `balance` field on an account — it is derived.

**What this ticket produces is a draft, not the pinned contract.** When the prototype lands, the PM extracts the handler shapes into the Epic's phase-2 ticket for the Owner's go. `api` does not build against these handlers until that happens.

- **Harness delta (strip):** three, and the first one **corrects a claim this workspace had been repeating.**
  1. **`--dump-dom` did not become usable again once the app mounted synchronously — and the reason the agent doc gave for that was wrong.** The doc blamed the async MSW bootstrap; deleting it changed nothing. `createRoot().render()` commits in a scheduler task *after* the load event, so the load-event snapshot beats React to the DOM on **any React 18+ root**, sync or not. In Chrome 151 `--headless=new` the process also never exits. **The PM predicted the opposite in the delegation brief** — a wrong rationale attached to a right rule is what invited that, which is the general lesson: a rule recorded without its true cause gets relaxed by the next person who thinks the cause is gone.
  2. **No `timeout`/`gtimeout` on this box** — a watchdog around a hanging browser needs a shell loop over `kill -0`, or a tool call burns its whole budget.
  3. **`Runtime.evaluate` has no top-level `await`** — wrap in `(async () => …)()` with `awaitPromise: true`, or a malformed check reads as a failing one.

- **Harness delta (phase 2):** six, folded into `.claude/agents/app.md`.
  1. **`[data-status="ready"]` alone stopped being a sufficient poll** the moment there was more than one view: an *in-page* transition leaves the old view still matching, so the poll returns instantly against stale DOM. Poll the compound `[data-view="X"][data-status="ready"]`.
  2. **Every terminal state must carry `data-status="ready"` — error states included.** A poll that only accepts the happy state hangs forever on a screen the app is never leaving.
  3. **Vite binds `::1` only** — `http://127.0.0.1:<port>` is connection-refused; use `localhost`. Chrome's CDP port is the opposite (v4), so `127.0.0.1:<debug-port>` is right. Mixing them up reads as a dead server.
  4. **`Intl.NumberFormat('vi-VN')` emits U+00A0 before `₫`.** Asserting `'0 ₫'` with a plain space fails against *correct* output. Assert `'0\u00a0₫'`.
  5. **Chrome logs every non-2xx as a console error**, so "console clean" cannot be `length === 0` on a suite that drives 401/409 paths deliberately. Classify expected vs unexpected.
  6. **A fresh `--user-data-dir` per run is load-bearing now, not hygiene** — the app persists to `localStorage`, so "empty browser storage" stops being a free precondition once any run has touched the profile. React controlled inputs also need the native value setter plus a bubbling `input` event; assigning `.value` does nothing.
  **PM's own delta:** a CDP `waitFor` expression must return a **boolean** — `document.querySelector(...)` under `returnByValue: true` fails to serialize a DOM node and the poll times out against a page that is actually correct. Use `!!document.querySelector(...)`. Cost the PM one false failure on this very ticket.
